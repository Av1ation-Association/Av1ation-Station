# Phase 3 — UI

**Goal:** every v0.1 screen implemented against the Phase 2 API, in three increments so that
something is demonstrable after each one, and so risk is retired early.

**Exit criterion:** all v0.1 journeys work in the desktop app *and* in a LAN browser with
identical behaviour, with per-field provenance visible, derived state rendered, logs
viewable, errors recoverable, and accessibility checks green.

---

## 1. Entry criteria

- [ ] Phase 2 exit checklist complete
- [ ] contract pipeline produces types for every endpoint in use
- [ ] spikes S1–S5 have verdicts (increments 2 and 3 depend on them; S5 gates the per-scene script template)
- [ ] **Penpot boards approved** for the increment's screens, per
      [frontend-penpot.md](../frontend-penpot.md) §9. Approval references are recorded
      in [progress.md](../progress.md).

No screen task below starts before its boards are approved. The design gate is a hard entry
criterion, not a parallel track: implementation transcribes approved boards rather than
inventing layout, so a missing board is a blocked task, not a design decision deferred to
code.

## 5. Cross-cutting requirements for every screen

Each screen is only done when it has all four of: **loading**, **empty**, **error**,
**populated**. A screen without an empty state and an error state is incomplete, regardless
of the happy path working.

Review checklist per screen:

- [ ] keyboard reachable and operable
- [ ] focus visible, order sensible
- [ ] `axe-core` clean (component test)
- [ ] `prefers-reduced-motion` respected
- [ ] no layout shift on load (skeleton matches final geometry)
- [ ] busy states for every action over ~300 ms
- [ ] destructive actions confirm and are undoable where possible
- [ ] URL reflects selection/tab so a reload restores context
- [ ] strings in the message catalogue
- [ ] works identically in the LAN browser

## 6. Deliverables

- Every v0.1 screen.
- Generated config renderer proving the contract pipeline pays off.
- Provenance UI for every field.
- Derived timeline with advisory freshness badges; no stored or derived `Stale` phase.
- Logs, export, Monaco, LAN mode.
- Scene editor, preview, and charts — if and only if the spikes pass.

## 7. Explicit non-goals

- i18n other than English (catalogue only).
- Mobile layouts (a phone can use the LAN UI, but it is not optimised).
- User-defined themes.
- Keyboard-only "vim mode".

## 8. Exit checklist

- [ ] every journey in §2–§4 works in desktop and in a LAN browser
- [ ] identical rendering and behaviour in both — no "desktop-only" affordances
- [ ] all screens have four states
- [ ] `axe` clean on every screen
- [ ] no component imports a transport
- [ ] no server data duplicated into Zustand
- [ ] no animation on layout properties
- [ ] keyboard parity for scene selection (if increment 3 ships)
- [ ] bundle budget respected (initial JS < 250 KB gz excluding Monaco/ECharts)
- [ ] `docs/progress.md` updated per increment

## 9. Known traps

| Trap | Avoidance |
| --- | --- |
| Re-rendering on every progress event | animate the bar from a ref; batch SSE per animation frame |
| 5,000-row scene list creating 5,000 DOM nodes | virtualization from the first commit of the list |
| Monaco in the initial bundle | dynamic import, separate chunk |
| Charts breaking in dark mode | chart theme reads CSS tokens, not hardcoded colours |
| Draft state lost on navigation | draft lives in Zustand keyed by route; guard prevents accidental loss |
| Bulk edit silently writing per-scene overrides | explicit scope choice |
| Two sources of truth for the lock | Query cache from SSE is the only client-side reflection |
